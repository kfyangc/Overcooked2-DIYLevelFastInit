# DIYLevelFastInit

Startup and memory optimization for the [OC2DIYLevel](https://github.com/gua248/Overcooked2-LevelEditor) custom-level plugin in *Overcooked! 2*. Requires BepInEx 5 and OC2DIYLevel 0.10.0 or 0.11.0.

[中文说明](README_CN.md)

## Source bundle conversion

Startup preparation now covers each map's top-level `info*` and scene `s_*` bundles and converts them to independent LZ4HC. Both single-block LZMA and bounded single/multi-block LZ4/raw inputs are supported, including ordinary independent LZ4 files generated by previous releases. The encoder searches up to 256 candidates in a 64 KiB hash-chain window and uses lazy match selection; this is an actual high-compression search, not a flag change. Every output block is encoded with the HC path and marked `0x03`, including incompressible data (at most the normal LZ4 bound of about 0.4% overhead), so already-HC bundles can be skipped without rewriting their timestamps. `common*` and runtime-owned resource bundles are unchanged.

Conversion keeps the full decoded data, scene/CAB node metadata and versions, verifies file and decoded-data hashes, then atomically replaces the original path. Source LZ4/raw blocks are decoded one at a time with an 8 MiB per-block limit; output is rechunked to 128 KiB. Single-block LZMA retains its bounded original dictionary. Unsupported compression layouts, including multiple LZMA blocks, retain their usable source files and are reported.

After replacement and hash verification succeed, the captured original and its recovery record are deleted. Failed replacements retain their recovery files. On later checks, old `original-*.bundle`/`.record` pairs are deleted only when the current optimized file and original backup both match their recorded hashes; unrelated, invalid or changed recovery data is retained and reported. No original is kept for a newly successful conversion, so it cannot be restored through the legacy restore setting.

`Loading.OptimizeInfoBundlesOnStartup` keeps its existing name and now controls both info and scene HC conversion. `Loading.RestoreOriginalInfoBundlesOnStartup` remains available for surviving legacy backups and takes precedence on startup. Look for `level bundle optimized in place; original discarded` and `level bundle optimization complete`. The version history below describes the earlier ordinary-LZ4 and backup-retaining behavior.

## Version 1.8.0

One DLL supports both OC2DIYLevel 0.10.0 and 0.11.0: the legacy optional-recipe factory hook is kept on 0.10, while 0.11 — where the old factory was removed — detects and hooks `CustomRecipeOptionalRegister.GetOrderDefinitionNode`. Custom recipe nodes, both lookup factories and cloned prefabs remain tracked; results shared across entry points are deduplicated by the existing ownership sets, and the selected optional-recipe target is logged at startup. The plugin display name is now localized.

Warm catalog sets are processed within an approximately 4 ms work budget instead of yielding a frame after every set; the budget is checked between sets, and a single set's I/O or object creation can still exceed it. Resident common bundles are rechecked before each load, skipping bundles completed by another plugin during an earlier wait. Directory order and complete, stable lightweight SOs are preserved. The `startup timing` log now breaks startup into per-stage timings covering info preparation, common resources, cache reads, lightweight object creation, cold-discovery loads, metadata extraction writes, cleanup waits and menus (`bundleMs` includes dependency-graph work and native container waits; `extractWriteMs` includes cold-scan creation and cache writes). Timings are wall time and nested phase totals must not be added twice. For a slow-startup report, retain logs from `LoadHeavy started` through `startup timing`, plus subsequent thumbnail warmup records, to distinguish catalog caching, common resources and source-image warmup.

First-time catalog generation no longer loads native info graphs: a single managed worker reads names, UID, scene names, dependency names and all four player settings directly from the serialized bytes, and only the main thread creates lightweight SOs and writes the existing cache format — no per-set collection waits when the direct read succeeds. Existing caches are reused, and catalog order and identity rules are unchanged. Direct reads cover type-tree serialized v17 files with bounded independent LZ4/raw UnityFS blocks and validate actual script identities and field layouts; unknown layouts, external scalar pointers or failed reads fall back to native discovery. Startup conversion still runs first per the existing settings; unconverted LZMA inputs fall back and initial conversion time remains. `catalog metadata read`/`source=metadata` mark direct indexing, `catalog metadata fallback` explains fallback reasons, and `startup timing` adds `metadataSets` and `metadataReadMs`. Set `Loading.EnableDirectCatalogReader=false` and restart to use native discovery.

## Version 1.6.18: optimize source info files at startup

Stop generating or loading separate LZ4 resource caches. On every startup, inspect each map's top-level `info*` files. Skip independent LZ4/raw layouts; convert supported single-block LZMA files serially on a managed worker, verify file hashes, full decoded-data hash, CAB/node directories and versions, then atomically replace the original path. Discovery, previews, host/client entry and original-mod callers all read the optimized source file.

Originals are retained as `.diylevel-fastinit/original-<GUID>.bundle` beside each map, with a `.record` containing the basename and before/after hashes. Backups and temporary files cannot enter top-level `info*` enumeration. Locked, unsupported, unwritable or invalid inputs remain unchanged and are reported. Commit/rollback retain complete recovery files; cancellation never writes a partial source bundle.

Settings in `BepInEx/config/oc2.diylevel.fastinit.cfg`:

- `Loading.OptimizeInfoBundlesOnStartup=true`: enabled by default. Disabling stops future conversions; it does not restore previously optimized files.
- `Loading.RestoreOriginalInfoBundlesOnStartup=false`: enable and restart to restore originals instead of optimizing. Both current and backup hashes must match the record; later map updates are preserved. Disable this option afterward; also disable optimization if the restored LZMA files should remain unchanged.
- Legacy `EnableLz4BundleCache` and `Lz4BundleCacheSizeMiB` options are ignored. Scalar catalog and thumbnail caches remain active.

Initial conversion adds startup waiting, shown as `DIY info checking ...`; later startups skip optimized files. Native info loading waits for preparation. Early multiplayer requests retain their copied envelope and acknowledge loading start, then wait for catalog readiness before resource work without announcing kitchen-ready early. Replacement invalidates fingerprinted catalog/thumbnail data once, and originals require additional disk space.

Look for `info bundle optimized in place` and the summary `info bundle startup optimization complete`. Subsequent `info bundle source: ... (source file)` lines refer to the original map path, which can now contain LZ4 data.

## Version 1.6.17

Extend the working 1.6.16 LZ4 cache to every compatible DIY `info*` bundle. Format version 2 is unchanged, so valid DMM caches remain reusable. All 20 installed info bundles are supported. Unsupported layouts fall back to the source and are remembered for the process; scene bundles, `common*`, and runtime-owned Qichi resources retain their original loaders.

The default published-data budget is now 2 GiB, configurable through `Loading.Lz4BundleCacheSizeMiB` (128–16384 MiB; restart required). The 20 converted bundles total 575.27 MiB, exceeding the previous 512 MiB limit. Existing-cache validation runs before new conversions. Background queuing neither refreshes existing LRU timestamps nor acquires leases. Until idle generation/validation completes, loads immediately use the source.

Fix the save dialog disappearing before asynchronous preparation: retain it from the save-ready callback and hold input with Team17 event-system suppressors while save work and UI Update continue. Preparation waits for save work without calling `Hide(false)`. Release owned suppressors on scene arrival; restore the current selection on cancellation/failure. Cover Don't Save, disconnects and official-level selections, with owner checks preventing an old request's cleanup from unlocking a new dialog.

## Version 1.6.16

Fixes generated LZ4 caches being rejected and subsequent entries using the original file. Versions 1.6.13–1.6.15 inherited the source LZMA block's `Streamed=0x40` flag for independent LZ4/raw blocks. The game's native reader then invokes its unsupported streamed LZ4 callbacks, reports `Failed to decompress data for the AssetBundle`, and persists a rejection marker. New blocks contain only compression flags `0x02`/`0x00`; compressed payloads and resource bytes are preserved.

Cache keys now include format version 2, isolating old bundles and rejection markers automatically. After upgrading, allow the frontend to idle until `bundle file cache built`, then confirm entry logs report `info bundle source: info_dmm (LZ4 cache)`. Startup identifies `format 2`, and persistent rejection now logs its reason explicitly.

The observed 1.6.15 entry used the original file: 7,597 ms bundle loading, 78 ms selected info, 7,926 ms preparation, then 3,566 ms from scene handoff to arrival. That run did not exercise LZ4 and cannot measure its benefit. Evidence is under `../.verification/perf-1.6.15/`.

## Version 1.6.15

Fixes first-time LZ4 cache creation on the game's bundled Mono runtime. Missing files/paths can throw `IsolatedStorageException`, which is not an `IOException`; checking an absent `.bad` or `.meta` previously aborted the job and left only `.lock`. The source reader also used a `FileOptions` constructor overload missing from this runtime; it now uses the supported five-argument overload. Missing files now produce a normal cache miss, and compatibility handling also covers files disappearing after the existence check. Worker errors retain their type/stack, and startup logs show the enabled cache directory.

Completed entries live under `BepInEx/cache/DIYLevelFastInit/bundles/` as hash-named `.bundle`/`.meta` pairs, not `.lz4` files. Version 1.6.15 converts only supported `info_dmm` files; 1.6.17 covers every compatible `info*`. Leave `Loading.EnableLz4BundleCache=true` and allow the frontend to idle after discovery/source-thumbnail work; entry/gameplay pauses conversion. `bundle file cache built` confirms publication, and `info bundle source: info_dmm (LZ4 cache)` confirms use. Existing `.lock` files can remain.

## Version 1.6.14

Entry, uncached previews and thumbnail prewarming now request the selected `LevelInfoSO` asset directly. The complete lightweight catalog and its stable SO identities remain unchanged. Cancellation drains native requests before dropping their pins and cannot start an obsolete fallback.

## Version 1.6.13

Adds a disposable LZ4 file cache for the installed `info_dmm` layout. A miss immediately loads the original file and queues conversion; one low-priority managed worker runs only while foreground loading and gameplay are idle. The original map is never overwritten. Cache entries are verified against source/output SHA-256 hashes once per process in the background, published with validated metadata, and limited to 512 MiB of published data. Unity bundle requests and resident containers pin their cache files until completion/unload. Rejected copies fall back to the original source and remain disabled for that source fingerprint.

Cache location: `BepInEx/cache/DIYLevelFastInit/bundles/`. Set `Loading.EnableLz4BundleCache=false` in the plugin configuration and restart to disable it, or delete the cache while the game is closed. Version 1.6.13 initially converts only supported single-block LZMA `info_dmm` files; 1.6.17 extends this to compatible `info*` files. Small scene bundles retain their original loaders. Conversion uses bounded streaming buffers and preserves directory nodes, CAB names and uncompressed resource bytes. The first use can still load from the original file while conversion/validation is pending. A paused conversion retains a read handle on its source until it resumes or shuts down; Windows may prevent overwriting that source during this period. Version 1.6.13 addresses file decompression; version 1.6.14 adds the object-loading change above.

The cancellation/save-handshake fixes from 1.6.12 remain in place:

This revision fixes load-request ownership across cancellation and reconnection, following Team17's per-connection loading and readiness flow:

- A cancelled client preparation immediately stops filtering save-ready messages, even while its native resource request is still draining. Successful handoff retains the filter only for that exact mailbox, peer and connection until the target scene arrives.
- Server preparation checks its request generation and network context after waits and before handoff. Returning to the frontend, resetting the connection or changing roles invalidates the old request; it cannot resume later as an offline load.
- Switching from a confirmed DIY save choice to an official DLC save request clears the old confirmation and cancels obsolete entry permissions before the host waits for save-ready. The official countdown and a later DIY selection can proceed while cancelled resource work drains.

The source layout introduced in 1.6.11 is retained. Resource requests still drain before their pins are released, and the original kitchen-ready handshake remains responsible for starting play.

## Limits

Bundle containers are still opened together with the transitive info dependencies of the selected scene/set. Inside an addressable container, only the selected level object graph is requested; this does not split the bundle file or remove assets referenced by that level. Original LZMA files can still require whole-block decompression, and unsupported direct addresses retain full-set fallback. Common bundles and resources retained by other mods remain outside this plugin's cleanup scope.

The first catalog scan, thumbnail prewarming, and first level entry still have I/O, decompression and configuration costs. Prewarming temporarily loads selected source graphs (or the compatible full-set fallback), with one image capture per frame and unused-asset collection between direct levels or fallback batches. Until a thumbnail is cached, its preview may take time to appear. With the optional thumbnail plugin absent, thumbnail prewarming is skipped. Single-player/host and normal remote-client preparation await native loads, but each individual configuration is still generated on the main thread; an expensive single configuration or Unity scene activation can still cause a frame spike. The client gate covers the vanilla reliable `LevelLoadByName` path; other mods calling the original client preparation method directly retain its synchronous fallback. Wait for initial catalog discovery before relying on the full list or joining a custom game.

The Qichi adapter delegates file reading and decoding to that runtime; its request startup can still block a frame. It covers the known `info_qichi` layout and does not discover arbitrary external packages belonging to other mods. Cold-start Qichi background rendering still needs gameplay verification.

## Install or roll back

Close the game, back up `BepInEx/plugins/DIYLevelFastInit.dll`, and replace it with the new DLL. To roll back the plugin, close the game and restore its DLL backup. Optimized info files remain loadable; use the restoration setting above first if the original files are also required. The metadata cache can be retained or deleted. Keep backup DLLs outside the plugins scan tree.
